# CI, dependencies and the SonarCloud secret

CI runs five GitHub Actions workflows from `.github/workflows/`:

- `ci.yml` runs on pushes and pull requests and has six jobs: `build`, `crd-reference`, `hl7-validator`, `mutation`, `gate-guard` and `gate`. `build` installs fhir-crd-router, runs `./mvnw -B verify`, then the [demo tour](replay.md#demo), the [UI journeys](../README.md#ui-interaction-tests), the [replay export](replay.md#embed-on-a-website), the leak scanner's self-test (`replay/test/leaks.test.mjs`), the bundle check and the Node regression suites, and uploads `demo-output/` and `site-dist/` as build artifacts. `crd-reference` runs the workbench against the [HL7 Da Vinci CRD reference server](api.md#run-against-your-own-endpoint), an implementation this project didn't write, and checks each verdict against what CDS Hooks 2.0 and CRD say the server's answers mean (`scripts/reference-runs.mjs`). `hl7-validator` checks `response.schema`, `response.coverage-information` and `response.coverage-location` against the pinned official HL7 FHIR Validator over the conformance corpus. `mutation` runs pitest on the `diagnostics` module and fails below the `pitest.mutation.floor` in `diagnostics/pom.xml`. `gate-guard` calls the shared [gate guard](https://github.com/dflippojr/.github#gate-guard), pinned by full SHA, which fails a pull request that deletes or skips tests, adds retries, or edits workflows or coverage config unless the owner applied `gate-change-approved`. `gate` always reports and fails unless `build`, `crd-reference`, `hl7-validator`, `mutation` and `gate-guard` all succeeded. The default-branch ruleset requires `gate` and `gate-guard`, both from GitHub Actions.
- `gate-guard-target.yml` posts the required `gate-guard` check from `main` under `pull_request_target`, so a pull request can't rewrite its own judge (`ci.yml`'s `gate-guard` job runs from the pull request's head and is only an early signal). It checks out no pull request code, and it counts the owner's label only when it was applied after the newest push.
- `sonar.yml` runs `verify` with JaCoCo coverage and the SonarCloud scanner, and fails when the SonarCloud quality gate fails. It runs on pushes to `main` and on pull requests from branches in this repository (forks get no secrets, so it skips them). A newer push cancels an older PR run; runs on `main` are never cancelled. The organization and project keys are in the parent `pom.xml`.
- `publish-replay-bundle.yml` runs after each green `ci` run on a push to `main` and publishes that run's `site-dist/` as the rolling replay bundle; see [The published bundle](replay.md#the-published-bundle).
- `review.yml` runs the automated pull request review once when a pull request opens (Dependabot PRs and forks are skipped). For a re-review after later commits, dispatch it: `gh workflow run review.yml -R dflippojr/payer-onboarding-workbench -f pr_number=<PR> -f mode=full`.

[AGENTS.md](../AGENTS.md) says how to run each gate job on your machine. `npm run ci:local` runs the same `run:` steps as `ci.yml`, in the same order, and stops the UI instance even when a step fails (JDK 21 on `JAVA_HOME`, Docker running for `crd-reference`; Git Bash on Windows). AGENTS.md also gives the commands to run the CRD reference runs, the HL7 validator and the mutation floor on their own.

`verify` also fails when a module's JaCoCo line coverage drops below its floor, the `jacoco.line.floor` property in that module's `pom.xml`. Each floor started at the measured coverage minus 1 point. Raise a floor when coverage rises; never lower one.

Dependabot (`.github/dependabot.yml`) checks Maven dependencies and GitHub Actions weekly and opens at most 3 pull requests per ecosystem, labeled `dependencies`. The root Maven reactor includes all five module POMs and the Maven wrapper; GitHub Actions updates cover `.github/workflows/`. Nothing auto-merges: CI decides whether each update is safe and the owner merges. Major Spring Boot bumps are ignored and handled as deliberate issues. The `fhir-crd-router` pin (`COMMIT=` in `scripts/install-crd-router.sh`) is invisible to Dependabot and stays a manual bump. So are the CRD reference server's two commits in `scripts/crd-reference-server.env`; its comment says how to bump them.

Same-repository Dependabot PRs run SonarCloud using a repository **Dependabot** secret named `SONAR_TOKEN`. In GitHub Settings → Secrets and variables → Dependabot → New repository secret, the owner must save an authorized analysis token under that exact name. Ordinary PRs and pushes use the existing Actions secret with the same name; Actions secrets are unavailable to Dependabot-triggered runs ([GitHub documentation](https://docs.github.com/en/code-security/reference/supply-chain-security/troubleshoot-dependabot/dependabot-on-actions)). If the token is unavailable, the workflow skips the scanner and reports a notice and job summary explicitly stating that no analysis was published and the quality gate was not evaluated. The separate CI workflow still runs the tests. Once the Dependabot secret and workflow are in place on `main`, trigger a new Dependabot PR update and verify that **Build, test and analyze** ran and SonarCloud published analysis for that PR's head commit. A notice-only run does not satisfy that verification.
